# Runner tool manifest — the single source of truth for what is installed in
# the assessment runner image.
#
# WHY THIS FILE EXISTS
# --------------------
# The tool inventory used to live in three places that could drift apart
# independently:
#
#   1. the apt-get install list in deploy/runner/Dockerfile
#   2. the `command -v` verification loop in the same Dockerfile
#   3. nothing at all on the Go side, so the authoring-time script validator
#      had no idea which commands a workflow could actually call
#
# Drift between (1) and (2) means a tool is installed but never verified, so a
# Kali wrapper-script rename silently produces a runner that is missing a
# command while the build stays green. Drift against (3) means an instructor
# can save a workflow calling `gobuster`, ship it to students, and only find
# out at grading time that it exits 127 — the exact failure class that cost us
# a full debugging cycle.
#
# All three now derive from this file. Adding a tool is a one-line change here.
#
# WHY IT LIVES UNDER internal/ RATHER THAN deploy/runner/
# -------------------------------------------------------
# Go's //go:embed cannot reference a path outside its own package directory,
# and the Go side is the consumer that most needs to stay honest. The
# Dockerfile can COPY from anywhere in the build context, so it is the side
# that bends.
#
# FORMAT
# ------
#   <check>  <package>
#
#   <check>    If it starts with '/', it is a filesystem path verified with
#              `test -e`. Otherwise it is a command name verified with
#              `command -v` and exposed to the script validator as a callable.
#   <package>  The apt package that provides it. Several checks may map to the
#              same package (impacket-scripts ships many binaries).
#
# Blank lines and '#' comments are ignored.
#
# SIZE BUDGET: the image must stay under 3 GB. Do NOT add kali-linux-large,
# kali-linux-everything, or metasploit-framework — each adds several GB and
# blows the runner Job's cold-pull budget.
